# Discovering prepared voice states on connection

Prepare voice fixtures before opening the bot's Gateway connection to model
users who were already in voice or streaming before the bot started.
Create the bot, guild, voice or stage channel, and member identities first using
the [test API](test-api.md), then call the shared voice-state fixture operation:

```bash
curl -X PATCH http://localhost:3000/_test/guilds/GUILD_ID/voice-states/USER_ID \
  -H 'Content-Type: application/json' \
  -d '{
    "channel_id": "VOICE_CHANNEL_ID",
    "self_stream": true,
    "self_video": false,
    "emit": false
  }'
```

`emit: false` prepares history silently, including when a Gateway session is
already connected. Discovery does not require a live `VOICE_STATE_UPDATE`.
Use `self_stream: false` for a voice-only user. The fixture operation also
supports the other voice flags; omitted values preserve existing state.
Session IDs are generated by Fauxcord, retained through moves and flag changes,
and replaced when a disconnected user rejoins.
A human user can be connected in only one guild: preparing a connected state in
another guild silently disconnects the earlier one, so snapshots show the user
only where they last joined. Bot users may be connected in several guilds; see
[one voice connection per human user](test-api.md#one-voice-connection-per-human-user).

Connect with IDENTIFY and the `Guilds` intent. After READY, Fauxcord sends a
`GUILD_CREATE` for each guild belonging to the bot's setup. Its `voice_states`
array contains saved connected states, preserving channel, user, session IDs,
`self_stream`, and the other voice flags. Each voice user's existing identity
is included in `members`, even when it falls beyond the usual first 1,000
members. Bot and human identities keep their stored `user.bot` value.

The [Discord GUILD_CREATE contract](https://docs.discord.com/developers/events/gateway-events#guild-create)
uses partial [voice state objects](https://docs.discord.com/developers/resources/voice#voice-state-object)
without `guild_id`; use the enclosing guild's `id`. Only states with a current
membership, user, and voice or stage channel in that guild are included.
Disconnected states (`channel_id: null`), removed members, deleted users or
channels, and states pointing into another guild do not appear. With no
connected states, `voice_states` is an empty array.

The `voice_states` snapshot does not depend on the `GuildVoiceStates` intent;
only live `VOICE_STATE_UPDATE` dispatches require it. Discord's documentation
describes `voice_states` as an unconditional
[GUILD_CREATE extra field](https://docs.discord.com/developers/events/gateway-events#guild-create-guild-create-extra-fields),
lists only `VOICE_STATE_UPDATE` and `VOICE_CHANNEL_EFFECT_SEND` under
[`GUILD_VOICE_STATES`](https://docs.discord.com/developers/events/gateway#list-of-intents),
and documents only `GUILD_PRESENCES` as changing `GUILD_CREATE` content
(`members` and `presences`). When intents were introduced, a Discord staff
member listed the `GUILD_CREATE` fields they filter
([discord-api-docs#1307](https://github.com/discord/discord-api-docs/pull/1307#issuecomment-581561519))
and named only `members` and `presences`. Major libraries (discord.js,
discord.py, JDA) read `voice_states` from `GUILD_CREATE` without checking the
intent. No captured payload without the intent is publicly available, so
Fauxcord follows the documented contract; if real Discord is observed to empty
`voice_states` without the intent, that would be a separate change.

A voice or stage channel keeps its type for its whole lifetime (see
[`POST /_test/setup`](test-api.md#post-_testsetup--create-an-environment)), so a
saved state can only disappear from `voice_states` through a disconnect or a
deletion, never through a channel conversion.

A new socket using fresh IDENTIFY receives a new snapshot of saved state,
including changes prepared while an earlier connection existed. This is
distinct from RESUME, which follows the existing replay behavior and does not
rebuild `GUILD_CREATE` snapshots. To make an already connected client
re-IDENTIFY without restarting it, use
[`POST /_test/gateway-session-invalidations`](test-api.md#forced-re-identify-of-a-live-gateway-session).
To make a reconnecting client's RESUME fail so it rebuilds state from a fresh
snapshot after a gap, arm it with
[`"trigger": "resume"`](test-api.md#failed-resume-trigger-resume); a silent
gap before detection can be produced with a
[zombie connection](test-api.md#zombie-gateway-connections).

`POST /_test/reset` clears voice fixtures while retaining bot, guild, channel,
and member registrations. A nonempty `token` limits cleanup to that setup's
guilds; an omitted or empty token clears all voice fixtures. Deleting a setup,
guild, user, or membership silently removes its affected voice fixtures.
Deleting a connected voice or stage channel through `DELETE /channels/:id`
instead disconnects its members like real Discord: the states are kept with
`channel_id: null` and live `VOICE_STATE_UPDATE` disconnects are sent (see
[Channel deletion disconnects members](test-api.md#channel-deletion-disconnects-members)).
Recreating deleted setup IDs does not restore the previous states. Unrelated
setups keep their fixtures after scoped cleanup.

These fixtures represent voice connection metadata and stream status. They do
not provide audio or video transport.
